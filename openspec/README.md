# OpenSpec в этом репозитории — краткий runbook

Не учебник по OpenSpec вообще (см. `openspec/AGENTS.md`, если сгенерирован
инструментом, или официальную документацию) — только то, что специфично
для *этого* репозитория: когда какой шаг использовать и в каком формате
просить агента.

## Когда вообще заводить OpenSpec-запись

```
Это архитектурное решение (новая capability, смена контракта
существующей, отказ от предыдущего подхода)?
├── Да  → propose → (apply, если есть код) → archive
└── Нет — это живой инцидент/точечный тюнинг конфига/фикс без изменения
      контракта поведения?
      → просто git-коммит с подробным сообщением (см. `git log` —
        например поднятие таймаутов, правки regex-эвристик). Заводить
        OpenSpec-запись НЕ обязательно.
```

Признак «архитектурное решение»: после него меняется хотя бы один
`## Requirement` в `openspec/specs/*/spec.md`, либо появляется новая
capability. Если после изменения текст существующих требований и сценариев
всё ещё описывает систему верно — это тюнинг, не архитектура.

Отдельно от OpenSpec — ADR в `docs/adr/`: туда идут развилки между
альтернативами и их обоснование (почему выбрано так, а не иначе), когда
решение не описывает поведение конкретной capability, а затрагивает
топологию/инфраструктуру целиком (например, на какой VM живёт сервис).
OpenSpec описывает ЧТО система должна делать; ADR — почему она устроена
именно так. Оба могут понадобиться для одного и того же изменения (см.
`openspec/changes/archive/2026-08-02-lighter-reranker-model-russian` +
`docs/adr/0026-*.md` за примером).

## Какую команду/skill когда

| Ситуация | Действие |
|---|---|
| Новая capability или заметное изменение контракта существующей, кода ещё нет | `openspec-propose` (или `/opsx:propose`) — сразу proposal.md + design.md + tasks.md + specs delta |
| Продолжить реализацию уже предложенного change | `openspec-apply-change` (`/opsx:apply`) — по `tasks.md`, с проверками из `operations.apply.guidance` в `config.yaml` (mypy/ruff/pytest → деплой → живой smoke-тест) |
| Мысли ещё не оформлены, нужно сначала обсудить/проверить гипотезу | `openspec-explore` (`/opsx:explore`) — не создаёт файлов, для прояснения перед `propose` |
| Change реализован и подтверждён вживую, пора закрыть | `openspec-archive-change` (`/opsx:archive`) — переносит delta в `openspec/specs/`, с проверками из `operations.archive.guidance` (подтверждённые вживую цифры, открытые риски со ссылкой на задачу) |
| Нужно поправить формулировку в главной спеке БЕЗ полного цикла change (опечатка, уточнение) | `openspec-sync-specs` (`/opsx:sync`) |
| Уже заведённый change нужно скорректировать (новые вводные, найдена ошибка в design.md) | `openspec-update-change` (`/opsx:update`) |
| Правка задним числом — поведение уже в проде, просто не задокументировано | Вручную по образцу `openspec/changes/archive/2026-08-0*-baseline-*` (proposal.md с `## Why` = «нет документации», tasks.md — все пункты сразу `[x]` с пометкой «baseline, implementация уже в проде»), затем `openspec change validate --strict <id>` → `openspec archive <id> --yes` |

## Формат запроса к агенту

Чтобы агент (Claude Code или другой) сразу знал, что делать, а не
переспрашивал:

- **Для propose**: сформулируйте *Why* (что не так сейчас/какой сценарий
  не поддержан) и, если уже есть, *What Changes* — конкретика, не
  «сделай нормоконтроль лучше». Живой пример из практики этого репозитория
  — «модель систематически не вызывает check_actuality сама, нужен
  precheck по образцу геометрии чертежей» (реальный proposal, см.
  `openspec/changes/archive/2026-08-02-baseline-actuality-check`).
- **Для apply**: просто «примени change `<id>`» — агент сам читает
  `tasks.md` и идёт по списку, отмечая `[x]`.
- **Для archive**: «архивируй `<id>`» ПОСЛЕ того, как живой тест на
  реальном стенде подтвердил поведение — не раньше (см.
  `operations.archive.guidance` в `config.yaml`).
- **Для точечного тюнинга** (не через OpenSpec): просто опишите
  наблюдаемую проблему с конкретными цифрами («таймаут 60с, реальный ответ
  занял 79.6с») — агент правит код + коммитит, без лишней церемонии.
